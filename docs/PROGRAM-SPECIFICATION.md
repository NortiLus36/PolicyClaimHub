# Policy Claim Hub — Program Specification

## 1. ภาพรวม

Policy Claim Hub เป็นระบบจำลองสำหรับจัดการกรมธรรม์ การรับชำระเบี้ย
และการวิเคราะห์สินไหมรถยนต์จากเหตุการณ์น้ำท่วมด้วยข้อมูล GIS
สร้างเป็น Portfolio เพื่อแสดงทักษะพัฒนาเว็บ ฐานข้อมูล Business Logic
Payment Integration, Spatial Analysis, RESTful API และ Oracle PL/SQL
ที่มี Business Logic สำหรับตอบโจทย์งานองค์กร

## 2. วัตถุประสงค์

- จัดการข้อมูลกรมธรรม์และสถานะความคุ้มครอง
- บันทึกการแจ้งเคลมรถยนต์จากน้ำท่วมด้วยตำแหน่งเกิดเหตุ
- ซ้อนทับจุดเกิดเหตุกับพื้นที่น้ำท่วมบนแผนที่
- ประเมินจำนวนเคลมและภาระสินไหมตามพื้นที่
- จำลองการรับชำระเบี้ยผ่าน Payment Gateway
- สาธิตการออกแบบ Oracle SQL, PL/SQL และ Spatial Data

## 3. ขอบเขตข้อมูล

- ใช้ข้อมูลบุคคล กรมธรรม์ รถยนต์ และตำแหน่งแบบจำลองเท่านั้น
- สูตรสินไหมเป็นกฎจำลองเพื่อการศึกษา ไม่ใช่เงื่อนไขของบริษัทประกันจริง
- Payment Gateway ทำงานใน Test Mode และไม่มีการเคลื่อนย้ายเงินจริง
- ข้อมูลน้ำท่วมต้องระบุแหล่งที่มา วันที่ของข้อมูล และ Attribution

## 4. ผู้ใช้งาน

### Admin

- จัดการผู้ใช้และข้อมูลอ้างอิง
- ดูและจัดการทุกส่วนของระบบ

### Agent

- เพิ่มและแก้ไขกรมธรรม์
- สร้างใบแจ้งชำระเบี้ย

### Claim Officer

- รับคำร้องเคลม
- ตรวจข้อมูลเหตุการณ์และเอกสาร
- ปรับสถานะการตรวจสอบ

### Approver

- อนุมัติหรือปฏิเสธสินไหม
- ระบุยอดสินไหมที่อนุมัติ

### Viewer

- ดู Dashboard และรายงานโดยแก้ไขข้อมูลไม่ได้

## 5. ความสามารถหลัก

### 5.1 จัดการกรมธรรม์

- แสดงรายการกรมธรรม์
- เพิ่มกรมธรรม์
- แก้ไขกรมธรรม์
- ดูรายละเอียดกรมธรรม์
- ค้นหาและกรองข้อมูล
- ตรวจเลขกรมธรรม์ซ้ำ
- ตรวจทุนประกัน เบี้ยประกัน และวันที่คุ้มครอง
- เลือกผลิตภัณฑ์ประกันรถยนต์และบันทึกข้อมูลรถ
- ระบุลูกค้าใหม่/ลูกค้าเดิมและข้อมูลติดต่อ

ข้อมูลพื้นฐาน:

- เลขกรมธรรม์
- ชื่อผู้เอาประกัน
- ทุนประกัน
- เบี้ยประกัน
- วันที่เริ่มและสิ้นสุดความคุ้มครอง
- สถานะกรมธรรม์
- ประเภทลูกค้า เบอร์โทรศัพท์
- ผลิตภัณฑ์ ทะเบียนรถ ยี่ห้อ รุ่น และปีรถ

### 5.2 การวิเคราะห์ลูกค้าและการต่ออายุ

- แสดงข้อมูลจำลอง 50 ลูกค้าในหน้าหลังบ้าน
- รวมจำนวนครั้งและยอดจ่ายสินไหมจากประวัติเคลม
- จำแนกความเสี่ยง `Low`, `Standard`, `Watchlist`, `High`
- คำนวณ Renewal Probability ช่วง 5-95%
- แนะนำเบี้ยต่ออายุและข้อความสำหรับเจ้าหน้าที่
- ค้นหาชื่อ เลขกรมธรรม์ ทะเบียนรถ และกรองระดับความเสี่ยง
- เปิดเผยผลผ่าน `GET /api/portfolio/renewal-insights`

กฎทั้งหมดเป็น Rule-based Simulation ที่อธิบายได้ ไม่ใช่ Machine Learning
หรือหลักเกณฑ์รับประกันภัยจริง

### 5.3 การเคลมรถยนต์จากน้ำท่วม

- เลือกกรมธรรม์ที่เกี่ยวข้อง
- บันทึกเลขที่เคลมและทะเบียนรถจำลอง
- บันทึกวันที่และตำแหน่งเกิดเหตุ
- ระบุระดับน้ำและความรุนแรง
- บันทึกยอดที่เรียกร้อง ยอดประมาณการ และยอดอนุมัติ
- เปลี่ยนสถานะตาม Workflow
- เก็บประวัติการเปลี่ยนสถานะ

Workflow ตัวอย่าง:

ฉบับร่าง → ยื่นคำร้อง → กำลังตรวจสอบ → รอข้อมูลเพิ่ม → อนุมัติ/ปฏิเสธ → จ่ายสินไหม

### 5.4 GIS และแผนที่น้ำท่วม

- แสดงพื้นที่น้ำท่วมเป็น Polygon
- แสดงตำแหน่งเกิดเหตุเป็น Marker
- Popup แสดงข้อมูลเคลมที่จำเป็น
- กรองตามเขต วันที่ ความรุนแรง และสถานะ
- วิเคราะห์ว่าจุดเกิดเหตุอยู่ภายในพื้นที่น้ำท่วมหรือไม่
- สรุปจำนวนเคลมและยอดสินไหมตามพื้นที่

ตำแหน่งที่จัดเก็บคือจุดเกิดเหตุที่ผู้ใช้แจ้ง ไม่ใช่การติดตาม GPS แบบ Real Time

### 5.5 Dashboard

- จำนวนกรมธรรม์ที่มีผล
- จำนวนเคลมน้ำท่วม
- จำนวนรถที่ได้รับผลกระทบ
- ยอดสินไหมที่ร้องขอ
- ยอดสินไหมประมาณการ
- ยอดสินไหมที่อนุมัติและจ่ายแล้ว
- ยอดเบี้ยที่เรียกเก็บ ชำระแล้ว และค้างชำระ
- เขตที่มีจำนวนเคลมหรือมูลค่าความเสียหายสูงสุด
- Estimated Loss Ratio จากข้อมูลจำลอง

### 5.6 Payment Gateway

- สร้างใบแจ้งชำระเบี้ยจากกรมธรรม์
- เปิด Stripe Checkout ใน Test Mode
- บันทึกรหัสอ้างอิง ยอดเงิน และสถานะธุรกรรม
- รับ Webhook และตรวจสอบ Signature
- ป้องกันการประมวลผล Webhook ซ้ำ
- แสดงประวัติการชำระเบี้ย

ระบบไม่จัดเก็บเลขบัตร วันหมดอายุ หรือ CVC
การจ่ายสินไหมให้ผู้เอาประกันจะจำลองด้วยสถานะ `ClaimPayment`
ไม่ใช่การโอนเงินจริงผ่าน Payment Gateway

### 5.7 Oracle และ PL/SQL

- มี DDL สำหรับตารางหลัก
- มี Seed Script สำหรับข้อมูลจำลอง
- มี Function คำนวณสินไหมจำลอง
- มี Procedure สรุป Dashboard ตามเขต
- มี Trigger หรือ Procedure สำหรับ Audit Log
- มีตัวอย่าง `SDO_GEOMETRY` และ Spatial Index
- แปลงข้อมูลระหว่าง GeoJSON กับ `SDO_GEOMETRY`
- Query จุดเคลมที่อยู่ภายใน Polygon น้ำท่วม

Business Logic ที่ต้องสาธิต:

- Function คำนวณสินไหมจากทุนประกัน ระดับน้ำ Deductible และหนี้ค้างชำระ
- Procedure ตรวจสอบและยื่นเคลม โดยกรมธรรม์ต้องมีผลในวันเกิดเหตุ
- Procedure อนุมัติเคลม โดยตรวจสถานะเดิมและจำกัดยอดอนุมัติ
- Package รวม Function และ Procedure ที่เกี่ยวข้องให้มี Public Interface ชัดเจน
- Query ใช้ CTE, CASE, Aggregate และ Spatial Condition เพื่อสรุป Exposure รายเขต
- Audit การเปลี่ยนสถานะเคลม

SQLite เป็นฐานข้อมูลหลักสำหรับ Demo ที่ติดตั้งง่าย
ส่วน Oracle ใช้สาธิตความสามารถและสามารถพัฒนาเป็น Provider หลักในอนาคต

### 5.8 RESTful API

- อ่านรายการและรายละเอียดกรมธรรม์
- เพิ่ม แก้ไข และลบกรมธรรม์ตามขอบเขตที่กำหนด
- ประเมินค่าสินไหมน้ำท่วมผ่าน Business Service เดียวกับหน้า MVC
- สรุปจำนวนเคลมและยอด Exposure ตามเขต
- ใช้ DTO แยกจาก Entity เพื่อควบคุมข้อมูลรับเข้าและส่งออก
- ใช้ DataAnnotations และ Server-side Validation
- คืน HTTP Status Code ให้สอดคล้องกับผลลัพธ์
- มีไฟล์ `.http` หรือชุด Request สำหรับสาธิตและทดสอบ

REST Endpoints ขั้นต่ำ:

- `GET /api/policies`
- `GET /api/policies/{id}`
- `POST /api/policies`
- `PUT /api/policies/{id}`
- `DELETE /api/policies/{id}` เมื่ออยู่ในขอบเขต Demo
- `POST /api/flood-claims/estimate`
- `GET /api/flood-claims/summary`

Oracle Package Integration ที่เพิ่มแล้ว:

- `GET /api/oracle-flood-claims` เรียก `PR_GET_CLAIM_PAGE`
- `POST /api/oracle-flood-claims` เรียก `PR_SUBMIT_CLAIM`
- `PUT /api/oracle-flood-claims/{id}/approve` เรียก `PR_APPROVE_CLAIM`
- `GET /api/oracle-flood-claims/health` ตรวจ Connection และ Package Status

ไม่มี Delete Claim เพราะต้องรักษา Audit Trail การยกเลิกใช้การเปลี่ยนสถานะแทน

Status Code ที่ต้องรองรับ:

- `200 OK`
- `201 Created`
- `204 No Content`
- `400 Bad Request`
- `404 Not Found`
- `409 Conflict`

## 7. กฎธุรกิจเบื้องต้น

- เลขกรมธรรม์ต้องไม่ซ้ำ
- จำนวนเงินทุกประเภทต้องไม่ติดลบ
- วันที่สิ้นสุดความคุ้มครองต้องอยู่หลังวันที่เริ่มต้น
- วันที่เกิดเหตุต้องอยู่ในช่วงที่กรมธรรม์มีผล จึงจะเข้าสู่การพิจารณาปกติ
- ยอดสินไหมที่อนุมัติต้องไม่เกินข้อจำกัดของสูตรจำลอง
- การชำระเบี้ยถือว่าสำเร็จเมื่อได้รับ Webhook ที่ตรวจสอบแล้ว
- ทุกการเปลี่ยนสถานะสำคัญต้องบันทึกผู้ดำเนินการและวันเวลา

## 8. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน

- Responsive และใช้งานได้บน Desktop และ Mobile
- Validation ทั้งฝั่ง Browser และ Server
- ไม่เปิดเผย Secret หรือข้อมูลส่วนตัวใน Source Control
- Log Error โดยไม่บันทึกข้อมูลบัตรหรือ Secret
- แยก Business Logic ออกจาก Controller เมื่อ Logic เริ่มซับซ้อน
- รองรับการทดสอบ Unit Test สำหรับสูตรคำนวณ
- README ต้องช่วยให้ผู้สัมภาษณ์ Clone และทดลองระบบได้
